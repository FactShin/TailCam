# TailCam 1.8.5 — reliable remote timelapse routing

Prepared 2026-09-11. [PR #85](https://github.com/FactShin/TailCam/pull/85), implementation commit `727824b8fdcc8b93cbb0f867d7ec9b4556055ab7`. Proposed patch release; not merged or published by this work.

A camera configured to capture on another computer now returns that computer's
rejection instead of silently creating a local timelapse. A read/write timeout,
invalid success response, or server error does not start a local duplicate.
Uncertain outcomes tell you to check the destination before retrying. The existing
local fallback remains for an unresolved destination or failure to connect, with
printer-analysis settings checked again on the actual local execution node.

The Timelapse screen shows the selected camera node, capture/storage node, and
configured printer-analyzer endpoint. Analysis and smoothing controls use the
execution node's capabilities. Configuration and successful node reachability
are distinguished from unverified AI/model readiness. Start results report the
actual owner, including when opened through the storage dashboard.

Motion events retain their recording's owner. REST, fleet aggregation, MCP
investigation, Events, Gallery, and the legacy event view use that owner when
opening a clip. Equal recording/event IDs on different nodes no longer select an
arbitrary match. Unresolved owners show unavailable rather than opening local media.

## Compatibility and data

- SQLite schema v12 adds `motion_events.recording_host` with an empty default.
  Existing media/files are unchanged. Historical remote events already lost their
  ownership; these cannot be repaired by guessing and retain their old meaning.
- Additive REST: `GET /api/timelapse-capabilities`, camera `timelapse/preflight`,
  and `GET /api/media/{id}`. Events add `recording_host` and nullable
  `recording_proxy_prefix`. Empty means local; null with an owner means unavailable.
- MCP `investigate_motion_event` adds optional `node_key`; it is required when
  the recent window contains the requested event ID on more than one node.
- Old nodes without the preflight endpoint show unknown capabilities; runtime
  start checks remain authoritative. Recording fallback behavior is unchanged.
- No data movement, model training/activation, deployment, or release publishing.

## Request-boundary fixes

- Remote timelapse camera IDs now receive the same validation as remote recordings.
- Generic proxy paths are checked before normalization can alter the target.
  Management, MCP, and nested proxy endpoints cannot be tunneled through it.
- Host validation covers reads as well as writes, including private footage and
  configuration. Supported addresses are localhost, IP literals, and full
  `*.ts.net` names; arbitrary custom DNS aliases are not accepted.
- Legacy event rows use text nodes instead of HTML interpolation for peer data.

These fixes do not create application-wide granular authorization. Ordinary REST
still relies on the existing network perimeter. Shared service authorization is
tracked in the roadmap. The frontend dependency audit still reports six existing
advisories (one high, five moderate); Vite/PWA and router upgrades need a separate
compatibility-tested PR. This release does not claim a clean audit.

## Validation

Fresh local checks on macOS with Python 3.12 and Node 22:

- `PYTHONPATH=src .venv/bin/pytest -q`: **563 passed**, three warnings (two
  dependency deprecations and the existing multi-method proxy OpenAPI operation ID).
- `PYTHONPATH=src .venv/bin/ruff check src tests`: passed.
- `PYTHONPATH=src .venv/bin/mypy src/tailcam`: passed for 125 source files.
- `npm run typecheck` and `npm run build`: passed; two production builds produced
  byte-identical assets. CI now checks typecheck/build and committed asset parity.
- Browser: desktop and 390px phone layout; source analyzer disabled with storage
  analyzer enabled; capture, mock analysis evidence, encoding, and owner-node
  smoothing all exercised successfully.
- Production Safari: Events opened and played the correct storage-owned clip
  from both dashboards despite colliding IDs and older paginated media. Unknown
  and offline owners showed errors without substituting the source's recording.
- Clean exported source built wheel/sdist; the sdist excludes scratch files and the wheel contains byte-identical dashboard assets.
- Baseline reproduction: the new remote-409 regression fails on main commit
  `3f2d5fd3785fd2ee498cf56ac90fee10d5f1f415` (returns 200 instead of 409), and passes
  with this change. No real cameras/AI services were contacted by these fixtures.

Regression coverage includes rejected/uncertain starts, fallback analyzer checks,
stale or unavailable capabilities, owner collisions, legacy migrations, URL-based
storage discovery, viewer-relative result routes, and request guards.
Separate source, storage, and mock Ollama processes verify HTTP routing, encoded
files and analysis evidence under independent media roots. A mock model is not a
real model-accuracy or hardware-capacity test.

Current cross-platform CI status is recorded on PR #85; local results above do not substitute for those jobs.
The first Windows run caught a locale-dependent decode in the new version-label
test; it now reads the UTF-8 HTML explicitly. The targeted version tests pass
locally, and the updated PR reruns Windows CI.

Real cameras, Raspberry Pi memory/thermal behavior, real GPU/model inference,
Windows/macOS/Linux live fleets, and long-duration captures remain release gates.
